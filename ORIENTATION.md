## Four constraints that change what advice is correct

1. **Determinism.** A seed must reproduce exactly, so the same seed must
   consume the same NUMBER of random draws. Any refactor that reorders
   generation silently changes every seeded run. There is a tool that
   hashes generated content across 20 seed/depth pairs
   (`tools/probes/fingerprint.gd`) so a change can be proven identical
   rather than assumed to be. Advice that ignores this is unsafe here.
2. **`src/sim` may not reference `src/render`.** That is what makes the
   whole game runnable headless, which is what makes ~1700 assertions
   possible. A proposed module that needs a renderer is not viable.
3. **One input vocabulary: keycodes.** Controllers are translated into
   synthetic keypresses and fed through the same door. Nothing downstream
   knows a pad exists. A synthetic press carries no modifiers, which has
   caused three separate bugs where an action was reachable only through
   a key a controller cannot produce.
4. **Comments carry reasoning, not description.** They record why a
   number is what it is, usually with the measurement behind it. They are
   the most information-dense part of the codebase; skipping them to save
   context will cost more than it saves.

## Before proposing that something be split out

Measure what the code REACHES FOR, not what its constants are named.
Constants clustering is not evidence that behaviour clusters. Measured on
this codebase: a proposed light module needed 11 fields of the central
object, a brazier module 9 across 14 functions. Those are not modules,
they are the same code with a prefix typed in front of every line — and
two objects that can disagree about one piece of state is the bug class
this project spends most of its effort preventing.

The one extraction that passed that test reached for nothing at all:
`src/sim/threat.gd`, pure arithmetic over a depth and a cell count.

## Not in src/

- `tests/run_tests.gd` — the suite. Large, and worth reading only for a
  specific question; the practices it embodies are in `DESIGN.md`.
- `tools/` — build scripts, publishing, and measurement probes. The probes
  answer questions rather than asserting; several findings quoted in
  `DESIGN.md` came from them.
- `assets/vaults/*.txt` — hand-authored rooms, a grid of characters with a
  small metadata header, validated by a linter in the suite.
